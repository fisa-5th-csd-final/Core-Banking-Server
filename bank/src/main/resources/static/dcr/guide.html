클라이언트 개발자를 위한 OAuth 2.0 / OIDC 여정

이 문서는 RP(Client) 애플리케이션이 Authorization Server와 연동해 로그인, 토큰 교환, 사용자 프로필 조회를 완료하기 위해 따라야 할 단계를 정리했습니다.

동적 등록 도구 열기

0. 사전 체크리스트

  • 서버 메타데이터 엔드포인트 /.well-known/openid-configuration에 접근 가능한지 확인합니다.
  • 동적 또는 정적 방식으로 클라이언트 등록 권한(또는 registrar 계정)을 확보합니다.
  • HTTPS, 리다이렉트 URI, CORS 등 프런트엔드 환경 설정이 실제 배포 환경과 일치하는지 점검합니다.
  • PKCE, state, nonce 등 필수 파라미터를 생성할 유틸리티가 준비되어 있는지 확인합니다.

1. OIDC 메타데이터 조회

Authorization Server의 OIDC Discovery 문서를 먼저 읽어 클라이언트 애플리케이션이 사용할 엔드포인트와 지원 기능을 파악합니다.

GET /.well-known/openid-configuration
응답에서 authorization_endpoint, token_endpoint, jwks_uri, scopes_supported, response_types_supported 등을 캐싱해 두면 이후 요청을 구성할 때 반복 호출을 줄일 수 있습니다.

2. 클라이언트 등록

동적 등록 (DCR)

클라이언트가 직접 등록을 수행할 수 있다면 /connect/register로 JSON 요청을 보냅니다. 이때 registrar 토큰이 필요하며, 도구가 필요하면 상단 버튼으로 이동하세요.

POST /connect/register
Authorization: Bearer <registrar_access_token>
Content-Type: application/json

{
  "client_name": "My OIDC Client",
  "redirect_uris": ["https://client.example.com/login/oauth2/code/main"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope": "openid profile email",
  "require_proof_key": true
}
정적 등록이라면 동일한 속성을 서버 담당자에게 전달하고, 발급받은 client_id, client_secret을 안전하게 저장하세요.

3. 로그인 요청 만들기

사용자를 인증하기 위해 Authorization Server의 /oauth2/authorize로 리다이렉트합니다. 필수 파라미터는 다음과 같습니다.

파라미터 설명 예시 필수 여부
response_type 대부분 code (Authorization Code Grant) code 필수
client_id 등록된 클라이언트 식별자 my-oidc-client 필수
redirect_uri 등록된 URI와 정확히 일치해야 함 https://client.example.com/login/oauth2/code/main 필수
scope openid 포함, profile/email 등 필요 범위 추가 openid profile email 필수
state CSRF 방지 토큰, 응답 비교 필수 OAuth2.0 스펙 상 CSRF 토큰을 삽입해야 하는 게 옳지만
테스트의 편의성을 위해서 적용하지 않았습니다.
빈 값으로 보내도 됩니다.		 선택
nonce ID Token 재생 공격 방지용 난수,
OPTIONAL		 random-nonce-xyz 선택
code_challenge, code_challenge_method PKCE 사용 시 필수. code_challenge_method=S256 권장 code_challenge=... 선택
SPA나 모바일 앱은 code_verifier와 code_challenge를 사용자 세션 저장소에 보관하고, 콜백 처리 시 교환해야 합니다.

4. 인가 코드 교환

사용자가 성공적으로 로그인하면 서버는 등록된 리다이렉트 URI로 ?code=...&state=...를 붙여 리다이렉트합니다. 클라이언트는 state를 검증한 뒤 다음 요청을 수행합니다.

POST /oauth2/token
Authorization: Basic <base64(client_id:client_secret)>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=<AUTHORIZATION_CODE>&
redirect_uri=https://client.example.com/login/oauth2/code/main&
code_verifier=<CODE_VERIFIER>

응답에는 access_token, refresh_token (옵션), id_token, token_type, expires_in이 포함됩니다. 보안을 위해 refresh_token은 서버 측에만 저장하세요.

5. 토큰 검증

ID Token

  • id_token의 서명을 jwks_uri에서 제공하는 JWK로 검증합니다.
  • JWT 클레임 중 iss, aud, exp, nonce를 확인합니다.
  • 다중 테넌트 환경이라면 azp, hd 등 추가 클레임도 점검하세요.

Access Token

  • 토큰이 JWT라면 동일하게 서명과 만료 시간을 검증합니다.
  • 토큰이 Reference 토큰이라면 Resource Server가 /oauth2/introspect로 상태를 확인할 수 있도록 구성하세요.

6. API 호출

Access Token을 Authorization 헤더에 담아 Resource Server API를 호출합니다.

GET /api/profile
Authorization: Bearer <access_token>
토큰 만료 시 refresh_token으로 새로운 Access Token을 발급받거나, 만료 임박 시 Silent Refresh 전략을 사용하세요.

7. 세션 및 로그아웃 관리

  • 클라이언트 자체 세션을 생성할 경우 id_token의 sub 값을 사용자 키로 삼습니다.
  • 서버 로그아웃을 연동하려면 RP-Initiated Logout URL(end_session_endpoint)을 호출하고, id_token_hint와 post_logout_redirect_uri를 전달하세요.
  • Refresh Token을 더 이상 사용하지 않을 경우 /oauth2/revoke로 취소 요청을 보낼 수 있습니다.

주요 엔드포인트 요약

엔드포인트 용도 인증
/.well-known/openid-configuration Discovery 문서 permitAll
/oauth2/authorize 사용자 인증 및 동의 authenticated
/oauth2/token 인가 코드 <-> 토큰 교환 client 인증
/oauth2/jwks 서명 검증용 키 세트 permitAll
/oauth2/introspect Access Token 유효성 확인 client 인증
/oauth2/revoke 토큰 폐기 client 인증
/connect/register 동적 클라이언트 등록 registrar Bearer

트러블슈팅

  • 로그인 페이지로 리다이렉트되지 않으면 /oauth2/authorize가 인증 필요 상태인지 서버 설정을 확인하세요.
  • 리다이렉트 URI 불일치 오류는 공백·슬래시 유무까지 일치하는지 확인합니다.
  • PKCE 오류는 code_verifier와 code_challenge 계산 방식이 동일(S256)인지 검증합니다.
  • invalid_client가 발생하면 클라이언트 인증 방식(Basic, post, private_key_jwt 등)이 서버 설정과 일치하는지 확인하세요.
  • ID Token 검증 실패 시 nonce 또는 aud 검증 로직이 누락되었는지 점검합니다.
